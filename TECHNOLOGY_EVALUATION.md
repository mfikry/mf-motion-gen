# MF Motion Gen 2.0 — Technology Evaluation

**Research date:** 23 November 2026 (Updated 24 November 2026 post-POC)<br>
**Status:** Accepted technology candidate for implementation (Phase 3 POC validated; production readiness and final architecture deferred to Phase 4).

## 1. Executive recommendation

The accepted candidate stack for implementation is:

- **Desktop shell:** Electron
- **UI:** React + TypeScript
- **HTML-to-video engine candidate:** HyperFrames (`@hyperframes/core`, `@hyperframes/engine`, `@hyperframes/producer`) — accepted candidate for implementation
- **Animation timeline:** GSAP, with paused timelines that can seek to absolute time/frame
- **Encoding:** FFmpeg through the engine/producer pipeline

Phase 3 POC has validated HyperFrames' HTML-first rendering, paused GSAP timeline seeking, and FFmpeg export capabilities across multiple benchmarks (Round 1 NEXUS and Round 2 Breaking News).

### Caveats & Non-Claims
1. **Renderer Parity Caveat:** While encoder parity (ProRes vs MP4) is consistently high (SSIM > 0.978), renderer-to-mezzanine parity (Preview vs ProRes) exhibits sub-pixel Skia rasterization variations on fractional borders and skewed CSS transforms (averaging SSIM 0.9319–0.9879).
2. **Incomplete Security Testing Caveat:** Spike tests confirmed basic offline resilience and non-execution of shell commands within the sandbox, but full production security (untrusted HTML execution, Chromium sandbox isolation, context isolation, and IPC surface lockdown in Electron) has not been tested and is an explicit release gate for Phase 4.
3. **No Production Readiness Claim:** HyperFrames is accepted as the implementation engine for Phase 4 application development, but production readiness is not yet claimed until full desktop packaging and end-to-end integration pass in Phase 6.

## 2. Evaluation criteria

1. Works naturally with HTML generated by an LLM.
2. Can seek to any frame deterministically.
3. Can produce final video frame-by-frame instead of real-time screen recording.
4. Can preserve CSS/SVG/canvas/WebGL visuals where supported.
5. Can keep preview and render behavior aligned.
6. Can be integrated into a Windows desktop application.
7. Can be distributed commercially with a manageable license/dependency model.
8. Can safely execute untrusted imported HTML/JavaScript.

## 3. Candidate comparison

| Candidate | Fit for this product | Decision |
|---|---|---|
| **HyperFrames** | HTML-first; Chrome frame capture; deterministic seek; FFmpeg export; GSAP adapter | **Accepted technology candidate for implementation** (Phase 3 POC validated; production security & packaging deferred to Phase 4) |
| Remotion | Programmatic video renderer, but authoring model is React components rather than plain HTML; licensing has an automation-product category | Do not choose as core unless React authoring becomes a requirement |
| Raw Playwright/Puppeteer | Useful browser automation and screenshots; by itself it does not define the motion project's deterministic timeline contract | Use for supporting tests/tools, not the main engine |
| Motion Canvas | Strong code-authored animation model, but not a natural direct importer for arbitrary AI-generated HTML | Not selected for initial workflow |
| Tauri + WebView2 | Lightweight desktop shell, but system WebView2 version is independently updated; render engine still needs its own controlled Chromium/runtime | Not preferred for this Node/Chromium-centric prototype |
| PixiJS/custom Canvas renderer | Useful for projects authored specifically for those APIs, but rebuilding around it narrows native HTML compatibility | Do not use as the primary rendering engine |

## 4. Why HyperFrames is the best fit

HyperFrames describes its composition source as HTML, CSS, media, and seekable animations. Its documented pipeline:
1. Loads the HTML composition.
2. Injects its runtime.
3. Waits for readiness gates (including fonts and images).
4. Seeks and captures frames through a Chrome BeginFrame-based engine.
5. Encodes captured frames with FFmpeg.

Its deterministic model uses an integer frame clock (`time = frame / fps`), no wall-clock timing, no unseeded randomness, no render-time network fetches, and fixed output parameters.

This is much closer to a true render engine than simply recording a browser window while an animation plays.

## 5. Important limitations and risks

### 5.1 Frame Adapter API maturity
HyperFrames documents its Frame Adapter API as v0/experimental. The core idea (seek by frame, deterministic output) is stable, but method signatures may change before v1.

**Mitigation:** wrap it behind an MF Motion Gen internal interface, pin a tested package version, and write conformance tests. Do not expose HyperFrames types throughout the whole app.

### 5.2 Animation runtime support
The documented first-party adapter is GSAP. CSS/WAAPI, Lottie, and other runtimes are listed as planned or require custom adapters.

**Mitigation:** instruct Gemini AI Studio to output paused GSAP timelines registered with the expected composition ID. CSS should primarily style the visuals; do not rely on uncontrolled CSS animation clocks for final rendering. Add other adapters only after dedicated tests.

### 5.3 Generic HTML is not automatically deterministic
An HTML page may use `Date.now()`, `requestAnimationFrame`, `setInterval`, `Math.random()`, CDN assets, or scripts that fetch from the network. Those can cause non-repeatable frames or missing assets.

**Mitigation:** require a documented MF Motion Gen HTML profile. Import may accept arbitrary HTML as text, but only compatible projects become render-ready.

### 5.4 API and CLI export differences
The current producer documentation lists programmatic MP4 and WebM configuration, while the rendering CLI documents MP4, MOV, and WebM, including ProRes 4444 MOV for alpha workflows.

**Mitigation:** explicitly test MOV export through the intended integration path. Do not assume every CLI format is exposed identically through the producer API.

### 5.5 High-resolution performance
The references include 3840×2160 at 30 and 60 fps. Documentation listing a frame rate or dimension is not proof that the user's hardware can render complex content at an acceptable speed.

**Mitigation:** benchmark 1080p30, 4K30, and 4K60. Record render time, peak memory, dropped/failed frames, and output comparison.

### 5.6 Security
HyperFrames is a rendering framework, not a guarantee that untrusted HTML is safe to execute. Electron's own documentation warns that arbitrary untrusted content is a severe security risk.

**Mitigation:** run imported content in a dedicated isolated rendering process/context; disable Node integration; enable context isolation and Chromium sandboxing; restrict navigation, popups, permissions, and network; expose no filesystem or privileged IPC; impose time/resource limits. Security tests are a release gate.

### 5.7 Licensing
- HyperFrames GitHub repository identifies the project as Apache 2.0.
- GSAP's current project information says GSAP and its plugins are free, including commercial use, subject to the current standard license.
- FFmpeg is LGPL 2.1-or-later by default, but optional GPL/nonfree components can change the applicable obligations. The exact distributed FFmpeg build and codec set must be audited before packaging.

Do not bundle a random FFmpeg executable. Record binary source, version, build configuration, and license notices.

## 6. Why not Remotion as the primary renderer

Remotion is a capable code-based video framework. Its core authoring model is React compositions, which is a less direct fit for an HTML-first Gemini AI Studio workflow. Its current licensing page also distinguishes automated video products ("Remotion for Automators") from manual creation and lists usage-based terms.

Remotion remains a valid alternative if MF Motion Gen later changes to a React-component authoring model. For the current HTML-first workflow, HyperFrames is the better match.

Reference: https://www.remotion.dev/docs/license/pricing

## 7. Why not raw Playwright as the renderer

Playwright can capture screenshots and mock passage of time. Its screenshot option to disable animations stops CSS animations/transitions or fast-forwards finite ones; that is not equivalent to seeking an animation timeline to every output frame.

Playwright is useful for UI tests and visual regression automation. It does not remove the need for a deterministic motion contract or a frame capture/encode pipeline.

References:
- https://playwright.dev/docs/api/class-page
- https://playwright.dev/docs/clock

## 8. Proposed division of responsibility

- Electron: application shell, native file dialogs, project management, preferences, and user-facing workflow.
- React + TypeScript: import panel, preview controls, timeline, output settings, render queue, and diagnostics.
- HyperFrames: HTML project parsing/runtime integration and frame-by-frame rendering pipeline (subject to POC).
- GSAP: recommended authoring timeline for deterministic motion.
- FFmpeg: video encoding and format conversion, with audited build/licensing.
- MF Motion Gen adapter layer: normalize imported projects and shield the app from HyperFrames API changes.

## 9. Prototype gates before stack approval

1. Generate/import one HTML project using the proposed Gemini prompt/contract.
2. Preview and seek to arbitrary timestamps, including backward and random order.
3. Render a complete MP4 at 1080p30.
4. Render the same project at 4K30 and 4K60.
5. Compare preview captures and exported frames at identical timestamps.
6. Repeat the render and compare frame images for determinism.
7. Test local fonts, SVG, images, glow, blur, gradients, transforms, masks, and glitch effects.
8. Test MOV ProRes 4444 alpha through the integration path.
9. Test multiple imported HTML files and asset folders/ZIPs.
10. Test blocked network access, path traversal, renderer crash, timeouts, cancellation, and recovery.
11. Test on the target Windows development machine and record render time and peak memory.

## 10. Provisional decision

**Proceed to a HyperFrames-based technical proof of concept. Do not start full application development yet.**

The POC must demonstrate source import, exact seeking, visual parity, output quality, asset portability, security isolation, and Windows performance. If HyperFrames fails a hard requirement, evaluate a custom Chromium + adapter + FFmpeg pipeline as fallback.
